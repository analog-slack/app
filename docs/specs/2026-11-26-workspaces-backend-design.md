# Бэкенд рабочих пространств

Первый сценарий покрывает создание пространства, вступление коллег по ссылке и управление участниками. API проектов и каналов остаётся задачей следующих модулей. Модуль рабочих пространств предоставляет им проверку актуального членства и роли.

## Выбранный подход

Рассмотрели одноразовые и многоразовые приглашения. Для приглашения команды выбрали многоразовые ссылки. Несколько ссылок могут действовать одновременно, с независимыми сроками и отзывом.

Для владения предлагается использовать существующий `Workspace.ownerId` как источник роли `owner`. В записи членства хранятся базовые роли `admin` и `member`. API возвращает все три роли. Хранение роли владельца в обеих таблицах потребовало бы синхронизировать два источника прав.

## Пространства и участники

Любой авторизованный пользователь может создать пространство. Одна транзакция создаёт пространство и членство владельца. Один пользователь может состоять в нескольких пространствах. Список моих пространств строится по членству. Карточка пространства и список участников доступны его действующим участникам.

| Действие | Владелец | Администратор | Участник |
|---|---|---|---|
| Создавать и отзывать приглашения, удалять обычных участников | Да | Да | — |
| Назначать и снимать администраторов, удалять администраторов | Да | — | — |
| Передавать владение пространством | Да | — | — |

Владелец и администраторы могут просматривать приглашения и отзывать любую ссылку своего пространства. Удалить текущего владельца из пространства или понизить его роль через управление участниками нельзя. Роль владельца меняется при передаче владения.

В рамках этого модуля доступ к ресурсам пространства открыт всем его действующим участникам. Удаление участника прекращает этот доступ. При повторном вступлении бывший участник получает роль `member`, даже если до удаления он был администратором. Авторство и история сохраняются.

Передача владения вступает в силу после подтверждения текущим владельцем и успешного запроса. Получателем может быть другой действующий участник пространства, включая администратора. Сервер проверяет обоих пользователей и в одной транзакции меняет `ownerId` и роль прежнего владельца на `admin`. Если одновременно поступают две попытки передачи от одного владельца, успешно завершается только одна. Конкурирующее удаление получателя также не может оставить пространство без участника-владельца.

## Ссылки-приглашения

- Ссылка по умолчанию бессрочная. При ограничении срока можно выбрать 7 дней, 30 дней или указать своё целое положительное число дней. Сервер считает срок от момента создания. Технический предел срока определяется при реализации.
- Каждое приглашение получает новый криптографически случайный токен. Сервер хранит его хеш и возвращает токен только при создании. Список приглашений содержит метаданные и состояние ссылок. Предлагаемый сценарий отправки — ручное копирование при создании.
- У бессрочной ссылки `expiresAt = null`. Состояния для API — активна, истекла, отозвана. Сервер проверяет срок при вступлении.
- Авторизованный пользователь без действующего членства может вступить по активной ссылке с ролью `member`. Приглашение не привязано к email. Ссылка остаётся активной после вступления.
- Если авторизованный пользователь уже состоит в пространстве, переход по известной ссылке открывает страницу этого пространства.
- Вступление проверяет отзыв и срок и создаёт членство атомарно. Уникальность пары `workspaceId` и `userId` гарантирует одно членство при повторах. После успешного отзыва вступление по ссылке невозможно. Уже вступившие коллеги сохраняют членство.
- Создание ссылки оставляет предыдущие ссылки действующими. Удалённый участник может вступить снова по действующей ссылке. Чтобы закрыть повторный вход по старой ссылке, её нужно отозвать.

## Бэкенд и проверка

Добавить модуль NestJS с операциями создания, списка и просмотра пространств, списка и управления участниками, передачи владения, создания, списка, отзыва и принятия приглашений. Использовать существующую проверку cookie-сессии для идентификации пользователя. Права проверяются по PostgreSQL. Описать контракт в Swagger для генерации клиента. Добавить миграцию Prisma для модели приглашений по ссылке без привязки к email. Подход к миграции ролей, маршруты, DTO, правила slug, HTTP-коды и механизм транзакционной синхронизации определяются при реализации.

Покрыть тестами основной сценарий, пользователя в нескольких пространствах, изоляцию доступа, матрицу ролей, несколько действующих ссылок, бессрочное и ограниченное приглашение, отзыв и истечение, переход действующего участника на страницу пространства, удаление участника и повторное вступление с ролью `member`. Отдельно проверить конкуренцию при вступлении и отзыве ссылки, а также при передаче владения и удалении получателя.
