# Frontend Engineering Standards & Agent Guidelines (Analog Slack)

Данный документ определяет фундаментальные архитектурные правила, технические требования и инженерные стандарты качества для фронтенд-части монорепозитория **Analog Slack** (`apps/web`, `packages/*`).
Все AI-агенты, субагенты и разработчики обязаны неукоснительно следовать этим требованиям при написании, рефакторинге, проектировании и ревью клиентского кода.
---

## 1. Суть продукта и сквозной сценарий фронтенда

**Analog Slack** — корпоративный рабочий мессенджер для команд разработчиков, объединяющий общение, управление задачами (Канбан), синхронизацию с GitHub, асинхронные стендапы, базу решений и контекстного ИИ-ассистента.

**Ключевой сценарий в интерфейсе:**

```text
Чат (канал/тред) ──► Клик «Создать задачу из сообщения» (с сохранением обратной ссылки)
                 ──► Отображение карточки на Канбан-доске (drag-and-drop)
                 ──► Получение WebSocket-события об открытии связанного PR
                 ──► Оптимистичный перенос карточки «На проверку»
                 ──► Merge PR ──► Уведомление в канал + статус «Готово»
```

### Структура фронтенд-монорепозитория

- `apps/web` — основное приложение (Next.js App Router, FSD v2.1, TanStack Query, Zustand, Socket.io-client).
- `apps/landing` — презентационный лендинг продукта (Next.js, Tailwind CSS).
- `apps/ui-docs` — Storybook и документация дизайн-системы.
- `packages/ui` — общий UI Kit (Radix UI, Shadcn UI, Tailwind CSS).
- `packages/icons` — библиотека иконок (Lucide + кастомные SVG).
- `packages/api` — сгенерированный API-клиент и хуки TanStack Query v5
- `packages/dto` — общие контракты данных, типы событий сокетов и Zod-схемы.
- `packages/types` — общие TypeScript-типы.
- `packages/utils` — переиспользуемые утилиты (`cn`, форматирование дат, ссылок).

## 2. Принципы AI Code Review (Senior Frontend Engineer)

Любой AI-агент при анализе и ревью кода действует строго на уровне **Senior Frontend Engineer**:

### Приоритет проверки:

1. Реальные баги, некорректная логика интерфейса и регрессии.
2. Утечки памяти (не снятые подписки `socket.off`, замыкания и утечки в `useEffect`).
3. Состояния гонки (race conditions) при асинхронных действиях, сокетах и drag-and-drop.
4. Нарушения слоёв и правил Feature-Sliced Design (FSD).
5. Просадки FPS и зависания длинных списков сообщений (отсутствие виртуализации).
6. Рассинхронизация клиентского кэша и серверных данных.
7. Доступность (a11y) и строгая типобезопасность.

### Запреты для AI Reviewer:

- ❌ **Не делать замечания ради количества.**
- ❌ **Не тратить ревью на форматирование** (за это отвечает Biome/Prettier).
- ❌ **Не придираться к субъективному неймингу** или стилистическим предпочтениям.
- ❌ **Не предлагать альтернативную реализацию**, если текущая корректна, безопасна и типизирована.

### Обязательный формат каждого замечания:

1. **Что неправильно** (файл, строка, проблемный код).
2. **Почему это проблема** (impact: утечка памяти, лишний ре-рендер, срыв скролла).
3. **Как исправить** (точный и лаконичный код).

## 3. Границы Monorepo для фронтенда (Dependency Inversion)

1. **Constitution Principle I (Изоляция пакетов):**
   - Пакеты `packages/*` **никогда не импортируют** приложения `apps/*`.
   - Сетевой пакет `@packages/api` объявляет контракт `HttpTransport`.
   - Приложение `apps/web` при инициализации внедряет свой авторизованный клиент `apiClient` в API-пакет через функцию `initApiTransport()` (Custom Mutator для Orval).
2. **Constitution Principle II (Запрет ручных API-типов и сервисов):**
   - Запрещено писать рукописные классы сервисов с ручными вызовами и дублировать серверные интерфейсы в компонентах.
   - Все хуки запросов (`useQuery`, `useMutation`) и DTO импортируются из `@packages/api` (сгенерированы через Orval из Swagger/OpenAPI спецификации NestJS).

## 4. Архитектурная методология: Feature-Sliced Design (FSD v2.1)

Код `apps/web/src` структурируется строго по слоям:

```text
apps/web/src/
├── app/       # Инициализация Next.js, глобальные провайдеры, роутинг
├── pages/     # Композиционные страницы приложения
├── widgets/   # Крупные самодостаточные блоки (Sidebar, ChatView, KanbanBoard, DecisionList)
├── features/  # Пользовательские действия (send-message, create-task-from-message, filter-kanban)
├── entities/  # Бизнес-сущности (message, task, channel, workspace, project, user)
└── shared/    # UI-примитивы, socket-синглтон, базовый fetch, утилиты
```

### Жесткие правила FSD:

1. **Направление зависимостей (строго сверху вниз):**
   `app` ➔ `pages` ➔ `widgets` ➔ `features` ➔ `entities` ➔ `shared`.
   Слой `shared` не зависит ни от кого.
2. **Запрет Cross-Imports:**
   Модули одного слоя **никогда не импортируют** друг друга напрямую (например, из `features/task-create` запрещено импортировать `features/task-edit`). Общая логика поднимается в `widgets` или опускается в `entities`/`shared`.
3. **Public API (`index.ts`):**
   Каждый слайс обязан иметь точку входа `index.ts`. Все внешние импорты разрешены **только через публичный API** (`@/features/chat`). Глубокие импорты вида `@/features/chat/ui/MessageItem` категорически запрещены.

## 5. Next.js App Router и защита роутов

1. **Server Components по умолчанию:**
   Директива `"use client"` ставится изолированно — только на интерактивные листовые компоненты с хуками React или подписками на сокеты.
2. **Группы маршрутов (Route Groups):**
   - `(guest)` — гостевая зона (`/login`, `/register`).
   - `(protected)` — рабочая зона мессенджера (`/channels`, `/tasks`, `/projects`).
3. **Декларативная защита (`AuthBoundary`):**
   - Роуты внутри `(protected)` оборачиваются в `<AuthBoundary mode="protected">`. Неавторизованные пользователи перенаправляются на `/login?returnTo=...`.
   - Защита от Open Redirect: параметр `returnTo` обязательно проверяется на относительный локальный путь (`returnTo.startsWith('/') && !returnTo.startsWith('//')`).
4. **Централизованный конфиг маршрутов (`ROUTES`):**
   - Все URL-пути страниц выносятся в единый конфиг `routes.ts` (`shared/config/routes.ts`). Строковые литералы путей запрещены в компонентах.
   - ⛔ **Запрещено использовать классы** (`class Pages`). Конфиг оформляется строго объектом с `as const`:
     ```typescript
     export const ROUTES = {
       HOME: '/',
       LOGIN: '/login',
       REGISTER: '/register',
       CHANNEL: (id: string) => `/channels/${id}`,
       TASK: (id: string) => `/tasks/${id}`,
     } as const;
     ```
5. **Динамические импорты (`next/dynamic`):**
   - Тяжелые интерактивные клиентские компоненты (виртуализированная канбан-доска, rich-text редактор сообщений) загружаются через `dynamic()` с отключением SSR (`ssr: false`) и скелетоном загрузки для уменьшения начального бандла.

## 6. TypeScript & React 19+

1. **Строгий режим (Strict Mode):**
   - Полный запрет типа `any`.
   - Тип `unknown` допустим только с обязательным сужением (Type Guards / Zod).
   - Запрещены слепые касты (`as Type`). Типы форм и контрактов выводятся из Zod через `z.infer<typeof schema>`.
2. **Объявление компонентов:**
   - ⛔ **Полный запрет на устаревший `React.FC` / `React.FunctionComponent`**. Компоненты объявляются как стандартные функции с типизацией пропсов в аргументах:
     ```typescript
     interface MessageItemProps {
       message: MessageDto;
       onReply: (id: string) => void;
     }
     export function MessageItem({ message, onReply }: MessageItemProps) { ... }
     ```
3. **Типизация событий форм (React 19):**
   - ⛔ **Запрещен устаревший `FormEvent`**. Для сабмита форм (`onSubmit`) использовать строго `SubmitEvent<HTMLFormElement>`.
4. **Формы и валидация:**
   - React Hook Form + Zod. Понятные сообщения об ошибках на русском языке под полями ввода.
   - Индикация `isSubmitting`: блокировка кнопки сабмита (`disabled`) и показ спиннера.

## 7. UI Kit, стилизация и UX высокой нагрузки

1. **Дизайн-система:**
   - Стек: **Shadcn UI** + **Tailwind CSS** + **Lucide Icons**.
   - **Запрет инлайн-стилей и кастомного CSS по месту:** только утилитарные классы Tailwind и CSS-переменные дизайн-системы (`bg-background`, `text-foreground`, `border-border`) для светлой и темной тем.
2. **Storybook (`apps/ui-docs`):**
   - Для каждого нового UI-компонента создается файл историй `ComponentName.stories.tsx`.
   - Обязательные состояния в историях: `Default`, `Loading` (скелетон), `Disabled`, `WithError`.
3. **Производительность чата с 10,000+ сообщений:**
   - **Обязательная виртуализация списков** длинных переписок (библиотека виртуализации на выбор, например `@tanstack/react-virtual`).
   - Постраничная дозагрузка истории сообщений (infinite scroll вверх) по курсору.
   - **Умный скролл:** приход нового сообщения НЕ должен срывать скролл вниз, если пользователь изучает историю наверху. При появлении новых сообщений снизу показывается плавающий баббл «Новые сообщения ↓».
4. **Оптимистичный UI и надежность отправки:**
   - Мгновенный оптимистичный рендеринг отправляемого сообщения с генерацией временного `clientGeneratedId`.
   - Статусы сообщения: `sending`, `sent`, `error`. При ошибке сети пользователь видит индикатор ошибки и кнопку «Повторить попытку».
5. **Доступность (a11y):**
   - Кнопки-иконки без видимого текста обязаны содержать понятный `aria-label`.
   - Модальные окна и шторки должны корректно захватывать и возвращать фокус клавиатуры.

## 8. Управление состоянием (TanStack Query vs Zustand)

### Главное дерево решений стейта:

```text
Какое состояние нужно сохранить?
│
├── Данные пришли с сервера (сообщения, каналы, карточки доски, треды)?
│   └── ► TanStack Query v5 (Server State)
│
├── Эфемерное UI-состояние для нескольких виджетов (свернут ли сайдбар, открыт ли тред)?
│   └── ► Zustand v5 (Client Global State)
│
├── Состояние ввода формы и ошибки валидации?
│   └── ► React Hook Form + Zod
│
└── Локальное состояние одного компонента (открыт ли dropdown)?
    └── ► useState / useReducer
```

### Жесткие правила стейт-менеджмента:

1. ❌ **Категорически запрещено сохранять данные из `useQuery` в сторы `Zustand`.** `useQuery` сам по себе является реактивным источником истины.
2. Подписка на сторы Zustand — **строго через точечные селекторы**, чтобы исключить лишние ре-рендеры:
   ```typescript
   const activeThreadId = useChatStore((s) => s.activeThreadId);
   ```
3. **Фабрика ключей (Query Key Factory):**
   - Организация ключей запросов — централизованно через фабрики объектов с `as const` или готовые генераторы ключей из Orval.
   - ⛔ **Запрещено использовать классы для хранения ключей** (`class QueryKeys`).
   ```typescript
   export const chatKeys = {
     all: ['messages'] as const,
     channel: (channelId: string) => [...chatKeys.all, 'channel', channelId] as const,
     thread: (threadId: string) => [...chatKeys.all, 'thread', threadId] as const,
   };
   ```
4. Для канбан-доски и реакций обязательны оптимистичные обновления (`onMutate` $\to$ `onError rollback` $\to$ `onSettled invalidate`).

## 9. Сетевой транспорт и безопасность авторизации

### Разделение сетевого транспорта (Axios vs Нативный Fetch)

1. **Клиентский API-транспорт для NestJS (Axios + Orval):**
   - Единый настроенный инстанс Axios (`apps/web/src/shared/api/client.ts`) используется как транспортный адаптер (Custom Mutator) для сгенерированных хуков Orval.
   - Обеспечивает отслеживание прогресса загрузки файлов (`onUploadProgress`) для вложений в чаты/задачи и централизованную работу с интерцепторами.
2. **Нативный `fetch` (строго 3 сценария):**
   - `middleware.ts` — проверка токенов в куках на Next.js Edge Runtime (Axios не поддерживается в Edge).
   - Стриминг ИИ-ассистента — чтение потока ответа через `ReadableStream` / Server-Sent Events.
   - Лендинг (`apps/landing`) и публичные SSR-страницы — интеграция с серверным кэшем Next.js `{ next: { revalidate } }`.

### Правила авторизации:

1. **Хранение токенов:**
   - Access-токен хранится **только в оперативной памяти** приложения (`authToken.get()`). В `localStorage` токен не сохранять (защита от XSS).
   - Refresh-токен передается в защищенной `HttpOnly` Cookie (`withCredentials: true` / `credentials: "include"`).
2. **Мьютекс обновления токенов (Promise Deduplication):**
   - При получении `401 Unauthorized` интерцептор ставит параллельные запросы в очередь ожидания единого промиса `refreshPromise`.
   - Выполняется тихий запрос на `/auth/refresh`. После успеха упавшие запросы прозрачно повторяются с новым токеном без вылета пользователя на страницу логина.

## 10. Механика WebSocket-транспорта (Socket.io)

1. **Синглтон и Handshake:**
   - Синглтон подключения Socket.io размещается в `shared/api/socket`.
   - **Запрет передачи долговременных JWT в URL:** перед подключением клиент запрашивает одноразовый короткоживущий тикет и передает его в объекте `auth: { ticket }` (или заголовке subprotocol).
2. **Защита от утечек памяти (Memory Leaks):**
   - В каждом хуке или компоненте, подписывающемся на сокет-события, в функции очистки `useEffect` **обязательна отписка**:
     ```typescript
     useEffect(() => {
       socket.on('message:new', handleNewMessage);
       return () => {
         socket.off('message:new', handleNewMessage);
       };
     }, [socket, handleNewMessage]);
     ```
3. **Синхронизация Realtime-событий с TanStack Query (Защита от гонок):**
   - Перед ручной модификацией кэша по событию сокета **обязательно отменять исходящие запросы**, чтобы старый фоновый HTTP-ответ не перезаписал свежее realtime-событие:
     ```typescript
     // 1. Отменяем старый запрос
     await queryClient.cancelQueries({ queryKey: chatKeys.messages(channelId) });

     // 2. Атомарно обновляем кэш сообщений
     queryClient.setQueryData<MessagesPage>(chatKeys.messages(channelId), (old) => {
       if (!old) return old;
       if (old.items.some((m) => m.id === newMessage.id)) return old; // Дедупликация
       return { ...old, items: [...old.items, newMessage] };
     });
     ```
4. **Дедупликация при реконнекте:**
   - Ведется скользящий буфер полученных `messageId` (Set на 1000 элементов) для фильтрации дублей сообщений после восстановления сети.
5. **Экспоненциальный Backoff и терминальные коды:**
   - Авто-реконнект с задержкой 1s $\to$ 2s $\to$ 4s ... макс. 30s.
   - Терминальные коды (кик из канала, отзыв авторизации) останавливают попытки реконнекта и редиректят пользователя.
6. **Присутствие (Presence):** закрытие одной вкладки браузера не должно сбрасывать статус пользователя в offline, если открыты другие вкладки.

## 11. Интерфейс ИИ-ассистента и базы решений

1. **Human-in-the-Loop (Безопасность действий):**
   - ИИ **никогда не изменяет данные автоматически** (не создает задачи, не перемещает канбан-карточки, не фиксирует решения) без явного подтверждения пользователя.
   - ИИ готовит **черновик** (Draft карточки задачи или решения). Пользователь видит интерактивный блок, проверяет поля и нажимает «Создать».
2. **UX генерации:**
   - Обязательные состояния генерации: `стриминг / индикатор загрузки`, `успех`, `ошибка`.
   - Если информации в канале недостаточно, интерфейс выводит понятное сообщение об этом.
   - Каждое утверждение ИИ должно сопровождаться **кликабельными ссылками-чипсами** на исходные сообщения чата или задачи.

## 12. Стандарты тестирования (Vitest + React Testing Library)

1. **Философия тестов:**
   - Тестировать поведение глазами пользователя через `@testing-library/user-event`.
   - Поиск элементов преимущественно по роли (`getByRole`) и тексту (`getByText`), а не по `data-testid` или CSS-классам.
2. **Обязательные краевые состояния в тестах:**
   - Состояние загрузки (`Skeleton`),
   - Пустой список (`Empty State`),
   - Ошибка сети с кнопкой повтора (`Error State with Retry`).
3. **Изоляция окружения:**
   - Перед каждым тестом сторы Zustand сбрасываются: `useStore.getState().resetStore()`.
   - Инстанс `QueryClient` пересоздается в `beforeEach` с флагом `retry: false`.
   - Сетевые запросы и сокеты мокируются на транспортном уровне (`baseFetch` или MSW), реальные сетевые запросы в тестах запрещены.

## 13. Git, CI/CD и регламент коммитов

1. **Пакетный менеджер:** строго **`pnpm`**.
2. **Формат коммитов (Conventional Commits):**
   - Валидация через `commitlint` и хук Husky.
   - **Обязателен `scope`**: `feat(chat): ...`, `fix(kanban): ...`, `feat(auth): ...`, `style(ui): ...`.
   - Сообщение пишется без точки в конце.
3. **Trunk-based Development:**
   - Короткоживущие ветки и Pull Request. Прямой пуш в `main`/`master`/`dev` запрещен.
4. **CI-проверки на каждый PR фронтенда:**
   1. `pnpm lint` (Biome / ESLint с правилами FSD),
   2. `pnpm typecheck` (`tsc --noEmit`),
   3. `pnpm test` (Vitest с проверкой покрытия),
   4. `pnpm build` (Next.js продакшн-сборка).
